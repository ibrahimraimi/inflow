Inflow's backend is a mix of high-performance Edge functions and standard Node.js server-side logic.

## Ingestion Service (`/api/track`)

The ingestion service is the most critical part of the system.

- **Runtime**: **Next.js Edge Runtime**. This ensures low latency globally.
- **Validation**: Every incoming request is validated against a **Zod** schema (`trackEventSchema`).
- **Geocoding**: We attempt to extract geolocation (City, Country) from Vercel headers. If unavailable (e.g., local dev), we fall back to a lightweight IP geolocation API.
- **Persistence**: Data is written directly to the `page_views` table.

## Analytics Service Layer

To keep API routes clean, business logic is encapsulated in `src/server/services/analytics.service.ts`.

- **SQL Aggregation**: The service uses **Drizzle ORM** and raw SQL fragments for complex aggregations like counting unique visitors (`COUNT(DISTINCT client_id)`).
- **Timezone Handling**: All calculations are performed using the website's configured timezone to ensure data consistency.

## Authentication & Authorization

- **Better Auth**: Handles session management.
- **Organization Middleware**: We use a custom pattern to ensure users can only access data for websites belonging to an organization they are a member of.
- **API Security**: Token-based authentication for external API access (planned).

## Rate Limiting

- **Upstash Redis**: Used for distributed rate limiting.
- **Implementation**: The `rateLimit` utility prevents abuse of the ingestion and auth endpoints. It uses a sliding window algorithm.

## Performance Considerations

- **Edge DB Connection**: We use the Neon serverless driver, which is optimized for ephemeral environments like Edge functions.
- **Async Writes**: Ingestion is a simple `INSERT` to minimize processing time. Heavy computation is deferred to the dashboard viewing phase.
